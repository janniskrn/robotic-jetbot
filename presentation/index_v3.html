itotal architecture of the code

Three layers, one direction, one file at the motors

2703 lines in 24 Python files, all written by us. The stock NVIDIA notebooks are untouched and used as building blocks only. Data flows one way, and the layers are separated by their imports, not by a comment.

Provable in one command: grep "^import|^from" perception.py decision.py control.py. Neither decision.py nor control.py imports jetbot, so neither can reach a motor.

itotal architecture of the code

What happens inside one camera frame

1 · cameraFrame224 by 224 pixels, about 21 per second
2 · perceptionThree modelsResNet18, TensorRT lane: visible, xcurve: class, sidecup: seen, row, x
3 · decisionState machineSix states, first matching branch wins
4 · controlSteering and speedPD with gains scaled by speed, curve feedforward
5 · motorsWheelsBehind a battery guard, a camera watchdog and a motor watchdog

The lane model runs on every frame. The curve model and the cup model take turns on alternate frames, because all three on every frame cost 12 ms more per step and the steering got worse.

Measured in the Task 1 runs: 29.8 ms per step with three models, 21.6 to 22.8 steps per second. TensorRT took one lane pass from 41 ms to 10.6 ms.

ii + iiisource code · the state machine

Six states, and four phases inside the swerve

phase 1 · brakeStand still 0.3 s. Turning while still rolling carried the robot into the lane edge
phase 2 · turn outTurn in place until the tape ahead is 13 degrees before horizontal, or leaves the image
phase 3 · arcOuter wheel 0.37, inner 0.30, until the tape looks horizontal again
phase 4 · turn inTurn back until the lane is found near the center and aligned

Every phase ends on a camera mark and has a time limit; the robot has no encoders and no gyro. Table and diagram: notebooks/mini_av/STATE_MACHINE.md and diagrams/state-machine.html.

Why a cup is three questions, not one. The model says a cup is there, the mask says how far it is, and the lane position says whether it is in the way. A cup standing beside the lane must not stop the robot, and a second cup behind the first must not count.

# decision.py
def cup_ahead(percept):
    if percept['lane_visible'] < config.LANE_VISIBLE_THRESHOLD:
        return None
    for x, row, _ in percept['cup_bands']:  # nearest first
        if abs(x - percept['lane_x']) < config.CUP_IN_LANE:
            return x, row
    return None

def cup_close(percept):
    cup = cup_ahead(percept)
    return (percept['cup_visible'] >= config.OBSTACLE_VISIBLE_THRESHOLD
            and cup is not None and cup[1] >= config.OBSTACLE_ROW)

ii + iiisource code · config.py and safety.py

No magic numbers, and four guards that cannot be skipped

config.py · 5 of 107 values
STEERING_KP = 0.15      # wheel speed difference per unit of lane_x (0.35 and a cubic term made the robot swing)
STEERING_KD = 0.06      # wheel speed difference per unit of lane_x change per second (damping; 0.03 let the swing grow at 0.39)
MOTOR_TRIM = -0.01      # added to the left wheel, subtracted from the right; positive corrects a drift to the left.
OBSTACLE_ROW = 91 / 224.0  # nearest red band in the lane at or below this row: the cup is close (about 40 cm). At 0.35
ARC_WHEELS = (0.37, 0.30)  # outer and inner wheel in the curve around the cup. A wheel moves only above about 0.24
safety.py · the numbers every driving program shares
MOTOR_TIMEOUT = 0.25  # seconds without a motor update before the watchdog stops the motors (the loop stalled up to 1.1 s)
STALE_TIMEOUT = 0.5  # seconds without a new camera frame before the robot stops (the camera froze on 2026-09-20)

  1. 1Every tuning value is in one file. Not one number is buried in the logic, so a value can be changed without reading the code that uses it.
  2. 2Each one carries the run that set it. The comment is not decoration: it is the evidence that lets us defend the value or roll it back.
  3. 3Distances are written as image rows. The camera gives 224 rows, so a distance is a row, and the centimetres come from a measured table.
  4. 4The four guards live in safety.py and are shared: battery before the start and under load, a new camera frame within 0.5 s, a motor update within 0.25 s, and motors stopped in finally.

The guards are not optional. CLAUDE.md requires all four in every program that drives, after the robot drove blind into a chair on one frozen frame on 20 September.

03_train.py · main() · the split that keeps the numbers honest
val = [r for r in rows if any(v in r[1] for v in args.val)]
train = [r for r in rows if not any(v in r[1] for v in args.val)]

Whole recording sessions are held out, never single frames. Neighbouring frames look almost the same, so a random split would report a model that is better than it is.

Three models trained this way: lane 2458 frames, curve 3276, obstacle 3147. Labels come from the color masks, so the reported accuracy is agreement with the mask, and the slide says so.

ivresults · task 2, the stop

Stopping in front of a cup 3 runs, 35 to 40 cm

A cup in the lane at row 77 slows the robot to 0.31. At row 91 it stops, with a 0.1 s reverse pulse, because at motor value 0 the board lets the wheels coast. If it still ends up closer than 20 cm it backs up once. It drives on only when no band is above row 85 and the lane is visible again.

Runs stop_s1d2_1 to 3, 5 November. Without the slow approach and the brake, a stop at 27 cm left the robot at 10 cm, measured with a ruler. The lane condition exists because a hand in front of the camera hid both cup and lane and the robot drove on blind.
