How the robot decides, every frame

1 · cameraFrame224 by 224 pixels
2 · perceptionThree modelsResNet18, TensorRT lane: visible, xcurve: class, sidecup: row, x
3 · decisionState machineSix states, priority order
4 · controlPD and speedGains scaled by speed, curve feedforward
5 · motorsWheelsBattery, camera and motor watchdogs

Models report numbers. Only our decision and control code reads them, and the exact geometry comes from two color masks, not from a model.

Why it looks like this. The stock example attaches the model to the camera, so the callbacks queue up and the robot steers on an image from a second ago. Ours pulls the newest frame and drops the rest.

# drive.py
frame   = wait_for_new_frame(camera, frame)   # newest frame, never a stale one
percept = perception.observe(frame)           # three models -> numbers
mode    = decision.update(percept, now)       # one state, fixed priority
left, right = controller.update(percept['lane_x'], percept['curve_probs'],
                                percept['curve_dir'], dt)
robot.set_motors(left, right)

Loop measured in the Task 1 runs. TensorRT took one lane pass from 41 ms to 10.6 ms.

Six states, priority settles conflicts

Order: halt, avoidance and recovery, stop, slow down, following. During the swerve the lane rule is off on purpose.

Why it looks like this. Priority is not a comment. It is the order the conditions are asked in, and the first match wins, so a cup cannot be overruled by a curve.

# decision.py, update()
if self.state == HALT: return HALT                     # 1, the run is over
if self.state == OBSTACLE_AVOIDANCE:                   # 2, lane not asked
    self.update_avoidance(percept, now); return self.state
if self.state == ROAD_RECOVERY: ...                    # 2, until the lane is found
close = cup_close(percept) and (self.stop_only or cup_in_lane(percept))
if self.close_frames >= OBSTACLE_FRAMES:               # 3, four steps in a row
    self.enter(OBSTACLE_AVOIDANCE, now)
if p_sharp > SLOW_DOWN_ENTER: self.enter(SLOW_DOWN, now)        # 4
if now - self.lost_since >= LANE_LOST_TIMEOUT: self.enter(HALT, now)  # 5

Seconds driven against a 60 s cap. Red ended in a lane loss. The curve model bought the sharp curve, not smoothness.

Each term came from a failure. P alone wobbled, so D damps it. Gain scheduling exists because at 0.40 the same correction moves the robot further before the next frame. The feedforward exists because a curve needs a steady turn, and its direction comes from the curve model after the lane position flipped sign in the curve that kept failing.

# control.py, update()
schedule = REF_SPEED / max(self.speed, REF_SPEED)   # gains shrink as speed rises
wanted   = schedule * (KP * lane_x + KD * change) + self.feedforward(curve_probs, curve_dir)
self.steering = limit_change(wanted, self.steering, RATE, RATE, dt)   # max 2.0 per second
self.speed    = min(curve_speed, steering_speed)    # whichever is slower wins

Stopping at a cup 8 stops, shown live

The robot stops when the band reaches row 88 for four steps, and drives on only when it climbs back above row 80. Two different rows, so a jittering reading cannot release it in front of the cup.

Why a row and not a yes or no. The model predicts where the cup is, so the stopping distance stays a constant we can retune without recording anything again, and the decision stays in our code.

# decision.py
def cup_close(percept):
    return (percept['cup_visible'] >= OBSTACLE_VISIBLE_THRESHOLD   # 0.5
            and percept['cup_row'] >= OBSTACLE_ROW)                # row 88 of 224

def cup_gone(percept):
    return (percept['cup_visible'] < OBSTACLE_VISIBLE_THRESHOLD
            or percept['cup_row'] < OBSTACLE_CLEAR_ROW)            # row 80, hysteresis
