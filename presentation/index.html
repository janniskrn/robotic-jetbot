A model never sends a motor command. It returns numbers, and only our decision and control code reads them. Exact geometry does not come from a model at all: two color masks measure the lane lines and the cup band, and the checks that end a maneuver use those.

Loop 21.6 to 22.8 steps per second with 24 ms of model time in the Task 1 runs, which carried two models. With the obstacle model added it is 29.8 ms per step. TensorRT took one lane pass from 41 ms to 10.6 ms.

Six states, and priority settles every conflict

Priority, highest first: halt, avoidance and recovery, stop, slow down, following. During the swerve and the recovery the lane rule is switched off on purpose, because the robot is deliberately off its lane.

What we decided. Priority is not a comment. It is the order the conditions are asked in, and the first match wins, so a cup can never be overruled by a curve and a lost lane can never be overruled by a cup.

# decision.py, update(): asked in this order, first match wins
if self.state == HALT:                       # 1, the run is over
    return HALT
if self.state == OBSTACLE_AVOIDANCE:         # 2, lane not asked at all
    self.update_avoidance(percept, now); return self.state
if self.state == ROAD_RECOVERY:              # 2, until the lane is found
    ...
close = cup_close(percept) and (self.stop_only or cup_in_lane(percept))
if self.close_frames >= config.OBSTACLE_FRAMES:   # 3, four steps in a row
    self.enter(OBSTACLE_AVOIDANCE, now)
if p_sharp > config.SLOW_DOWN_ENTER:         # 4, cap the speed
    self.enter(SLOW_DOWN, now)

Same track, same lane model. Both stock runs lost the lane at about 20 s, and the plain PD run was the steadiest of all, so the curve model bought the sharp curve rather than smoothness.

What we decided, and why each number exists. P alone wobbled. The D term damps it. Gain scheduling exists because at 0.40 the same correction moves the robot further before the next frame, and the robot swung on the straight. The feedforward exists because a curve needs a steady turn that P only gives once the error is already large, and its direction comes from the curve model after the lane position flipped sign in exactly the curve that kept failing.

# control.py, update()
schedule = REF_SPEED / max(self.speed, REF_SPEED)   # 0.32 tuned, slower gains when faster
wanted   = schedule * (KP * lane_x + KD * change) + self.feedforward(curve_probs, curve_dir)
self.steering = limit_change(wanted, self.steering, RATE, RATE, dt)   # max 2.0 per second
self.speed    = min(curve_speed, steering_speed)    # whichever is slower wins

Eight stops in front of a cup shown live

The questionHow it is answered
Is a cup therethe obstacle model, above 0.5
How close is itthe lower edge of its red band, at row 88 of 224
Am I surefour control steps in a row
When may I drive onthe cup unseen, or its band above row 80, for five steps

The release row is farther away than the trigger row on purpose. With both at the same row, a reading jittering across it released the robot while it still stood in front of the cup. A person lifted the cup away after each stop.

What we decided. The model predicts where the cup is, not whether the road is blocked. That way the stopping distance is a constant we can retune without recording anything again, and the decision stays in our code.

# decision.py
def cup_close(percept):
    return (percept['cup_visible'] >= OBSTACLE_VISIBLE_THRESHOLD   # 0.5
            and percept['cup_row'] >= OBSTACLE_ROW)                # row 88 of 224

def cup_gone(percept):
    return (percept['cup_visible'] < OBSTACLE_VISIBLE_THRESHOLD
            or percept['cup_row'] < OBSTACLE_CLEAR_ROW)            # row 80, hysteresis

What we decided. The JetBot camera returns the same object when its thread has died, so comparing pixels proves nothing. Identity is the only honest proof that a frame is new, and the robot is allowed to move only while that proof keeps arriving.

# safety.py, imported by every program that can move the robot
while camera.value is old:            # the same object means no new frame
    if time.time() - start > timeout:  # 0.5 s
        raise CameraFrozen()
    time.sleep(0.005)

A camera freeze at 46.6 s in a later run was caught by exactly this check, which is the evidence it works.
